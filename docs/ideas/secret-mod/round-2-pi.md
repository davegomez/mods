# Round 2: Pi final review

The merged direction is acceptable. Four items block calling this the agreed final design.

B1. Supply the missing API citations and mark incomplete contracts UNVERIFIED. Slice 1 names most events and UI/API calls without the required file-and-section provenance. Add a compact source map covering the 1a table, command/tool registration, pane controls, continuation, file reads, clock/budget and process calls. Exact failure/result shapes remain gates, not established facts. Sources: `docs/mods/reference.md`, “Events”, “Mods API methods”, “Render sites” and “Elements”. `docs/mods/create-a-mod.md`, “Get type definitions for your version”, says installed declarations outrank pages. Also change “fetch has no setting to refuse [redirects]” to “the supplied docs confirm automatic redirects but do not document a refusal setting”. Absence from these pages is not proof no such setting exists.

B2. Resolve enrollment persistence and reset semantics instead of referring to absent Q10. Either make enrollment explicitly session-only and require re-enrollment after reload, or specify the non-secret config location, ownership, path scope and explicit user approval before accepting changed file/name lists. A repository-editable config must not silently authorise new file reads. Clear learned-value references on `session.end`, including `/clear`, `/resume` and `/branch`, then require explicit enrollment or approved refresh before showing active protection. No secure-erasure claim. Sources: `docs/mods/build/draw-in-the-interface.md`, “Keep state”, and `docs/mods/reference.md`, “Session”. Module variables survive ordinary turns, `session.start` does not run after those reset commands, and `session.end` does.

B3. Define the request state machine and validation. Validate `name` against a bounded environment-name syntax and limit/sanitise the untrusted reason before UI display. A tool request must report the actual status rather than always saying “not set”. Specify one pending request or a bounded queue, how requests are superseded, and that Stop, reset, reload or a newer task makes an old Continue button unusable. Consume Continue before submitting, handle rejection/drop, and never retry automatically. Otherwise the UX can resume the wrong task or submit twice. Sources: `docs/mods/build/use-the-mods-api.md`, “Add a tool”, “Start a turn from a background job” and “Calls and background work after the user interrupts a turn”. The documented submit waits for idle and can be dropped or refused.

B4. State failure boundaries and degraded states explicitly. A stale source must not still show Set or active protection. Keep old matches as best effort, report the refresh failure and say new values may not be protected. For an oversized, too-deep or unsupported text-bearing result, withhold even when no secret was found in the scanned part. Finally, `.catch` reduces fail-open behaviour but cannot guarantee it: its own failure skips the hook, and a worker crash/unload removes the shield. Record that limit alongside the promise and test it. Sources: `docs/mods/build/react-to-events.md`, “Handle a hook that fails”, `docs/mods/reference.md`, “Limits”, and `docs/mods/test-and-troubleshoot/troubleshoot.md`, “A hook is skipped or a mod is unloaded”.

No objection remains to deferring the companion, native collection, atomic writing, host warnings and authenticated operations. I reviewed the design only. No runtime, platform or provider behaviour was verified.
